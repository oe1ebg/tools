# AGENTS.md

This file provides guidance to AI coding agents (including Claude Code) when working with code in this repository.

## What this repo is

Standalone browser tools (plain HTML/CSS/ES modules, no framework, no server code) for radio amateurs: `tools/confirm/`, `tools/notfunk/`, `tools/adif/`, `tools/sota-alerts/`, plus `tools/shared/`. Published at https://oe1ebg.at/tools/ (the oe1ebg.at site consumes the release tarball) and meant to be deployed by others, including on webservers without internet. `README.md` covers usage, deployment, releases and the stable identifiers; each tool's own `README.md`/`AGENTS.md` its design.

Hard rules:
- **Self-contained bundle.** Every URL inside `tools/` and the rendered manuals is relative and stays inside the bundle (`../shared/…`, `../<manual>/`, `../`). No CDN, no external fonts, no absolute paths, nothing that assumes a host name or the `/tools/` prefix. Only the SOTA Alerts Map may use the network at runtime (it is documented as online-only).
- **Stable identifiers.** Never rename the `oe1ebg-*` IndexedDB/localStorage/BroadcastChannel names, the `OE1EBG_DATA`/`OE1EBG_SW` globals or the `APP_OE1EBG_*` ADIF fields: users' logbooks and exports depend on them.
- **Deployment headers.** `deploy/nginx.conf.example` and `htaccess.example` send a CSP per location: inline scripts only by sha256, `'unsafe-inline'` only for the single-file bundles, the SOTA Alerts Map's hosts only under `sota-alerts/`. Changing an inline script or a SOTA network host means changing both files; `tests/deploy-headers.test.mjs` checks them.
- **Data is built in.** `tools/shared/data/` and `tools/sota-alerts/data/` are generated (`just data`), inlined into the single-file bundles and part of the service-worker precache hash; a data refresh is a full bundle rebuild.

## Commands

`just` lists all recipes (`Justfile`). Main ones: `just build` (data + offline bundles + `site/tools/`), `just serve`, `just test`, `just e2e`, `just vnu`, `just crosscheck`, `just dist` (release tarball). `just data` and the `fetch-*`/`build-*` data recipes cache downloads in `.cache/`; `refresh-*` and `build-adif-spec` rewrite committed snapshots (`data-src/`, `tools/shared/js/adif-spec-data.js`) and are manual on purpose.

`scripts/build_site.py` (`just stage`) assembles `site/tools/`: `tools/<tool>/` without Markdown/dotfiles, the manuals `docs/*.md` rendered to `<name>/index.html` (python-markdown, links rewritten from MkDocs style), `docs/img/`, an overview `index.html` and `manifest.json`.

### CI

- `.github/workflows/ci.yml` — `changes` (scope), `test` (node tests, ADIF cross-checks), `bundle` (`just build`, then the node tests again with `DATA_TESTS=require`), `validate` (Nu Html Checker + Playwright per browser project against the bundle in nginx with `deploy/nginx.conf.example`).
- `.github/workflows/release.yml` — on `vX.Y.Z` tags: `just dist` with fresh data, tests with the ADIF cross-checks and the real-data checks required (`ADIF_CROSSCHECK=require`, Go tools built by `tests/tools/build.sh`; `DATA_TESTS=require`; a failure stops the release), then `validate-dist.yml` on the exact tarball (checksums, unpacked into a release directory behind a symlink at `/a/b/tools/`, nginx with `deploy/nginx.conf.example`, Nu Html Checker + Playwright in all five projects), and only then, in the `publish` job, provenance attestation, GitHub release with the tarball, `.sha256` and `SHA256SUMS`. The run's URL (`BUILD_RUN_URL`) goes into the ADIF editor's `build-info.js`, shown in its compliance panel.
- `.github/workflows/data.yml` — weekly: rebuilds the newest release tag with fresh data (same required checks and `validate-dist.yml`, `GIT_SHA` = the tag's commit) into the rolling prerelease `data-latest`; new assets are uploaded before stale ones are deleted.
- Pinning: every action pinned to a full commit SHA with a `# vX.Y.Z` comment; images as `tag@sha256:digest` (`tests/e2e/images.Dockerfile`, `tests/tools/images.Dockerfile`, never built, read by CI); Python via `.python-version` + `uv.lock`; Node via `.nvmrc`. `.github/dependabot.yml` keeps them current.
- **CI scope** (`ci.yml`, job `changes`, `dorny/paths-filter`): a PR runs the unit tests, the bundle build, the HTML check and the browser tests in all five Playwright projects, one `validate (<project>)` job each. A push to `main` runs the browser tests in Chromium only. The weekly scheduled run and manual runs check everything. The **ADIF checks** (`tests/adif*.test.mjs`, `tests/confirm-adif-spec.test.mjs`, the Go cross-checks, browser tests tagged `@adif`) run only when the `adif` filter matches (release and data builds always require the cross-checks); bundle, HTML check and browser tests only when the `site` filter matches (`tools/`, `docs/`, `scripts/`, `data-src/`, `tests/e2e/`, `deploy/`, `Justfile`, Python deps). Changes to `ci.yml` or `.nvmrc` match both.

Tests: `tests/*.test.mjs` (`node --test`, run via `just test`); they cover the confirmation log, the ADIF editor's exports and bundle, the SOTA Alerts Map's pure modules and summit lookup order, `tools/shared/` (including the location lookup's gold set, which only runs once `build-location` has produced the real data; the real-data tests skip without it unless `DATA_TESTS=require`, `tests/real-data.mjs`), the ADIF 3.1.7 conformance of both ADI exports (`tests/adif-spec.mjs`, a strict reader), the official ADIF test QSOs (`tests/adif-official.test.mjs`: the whole file and per group, validator without issues, ADIF editor export without errors and with every value kept), the ADIF validator (`tests/adif-validate.test.mjs` with the fixtures in `tests/fixtures/adif/`; `tests/adif-validate-snapshot.test.mjs` pins its and the ADI export's output byte for byte, `UPDATE_SNAPSHOT=1` only for intended changes), the ADIF cross-checks (`tests/adif-crosscheck.test.mjs`: fixtures, official test QSOs, both tools' exports and single invalid/edge values against adifmt and adif-checker, see below), the CI JUnit reporter (`tests/junit-reporter.test.mjs`), the deployment headers against the pages (`tests/deploy-headers.test.mjs`), and the HTML/interop rules for every tool page (`tests/tools-html.test.mjs`; the rules are in `tools/shared/README.md`, "HTML & interop rules"). No linter is configured. CI runs the tests (`test` job in `ci.yml`) before it builds the oe1ebg image.

ADIF cross-checks: a failing cross-check is **not automatically our bug**. adifmt and adif-checker have their own gaps and deviations (several are recorded already). Before changing the validator or an export, look the case up in the ADIF specification (https://adif.org.uk/317/ADIF_317.htm and the resources page) and find the correct behaviour; then either fix our code or record the tool's deviation in the test case's `differs` with the spec section, and in the table in `tools/adif/README.md` ("Cross-checks with other tools"). Never just flip an expectation to make the test pass.

Browser tests: `tests/e2e/` (outside the `tests/*.test.mjs` glob). `playwright.config.mjs`, the specs `*.spec.mjs` (confirm, notfunk, adif, sota-alerts, the offline bundles opened from `file://`, the response headers of `deploy/nginx.conf.example` — `Cache-Control`, CSP and the other security headers — which `serve.py` reads from that file), and `fixtures.mjs`. Through that fixture every test fails on a page error, a console error (a CSP violation included), a same-origin HTTP error, or an unstubbed request to another host. sota-alerts stubs the SOTA API and tiles with `page.route()`. They open `tools/<tool>/` below `BASE_URL`; run them in CI (`validate`, against `deploy/nginx.conf.example`) or locally with `just e2e`.

## Architecture notes

- **Tool HTML**: every page under `tools/` follows the "HTML & interop rules" in `tools/shared/README.md` (browser floor Safari 15.4 / Firefox 115 ESR / Chrome 109, shared `theme.js` + `tools.css` + the tool's `style.css`, no inline styles or handlers, no `innerHTML` with data, labelled controls with ARIA state). Interoperability is most important for the confirmation log.
- **Shared tool code**: `tools/shared/` (published at `/tools/shared/`) holds what several tools use: the location lookup and the location field, callsign and repeater completion, time helpers, the offline/update code and service worker logic (`offline.js`, `sw-core.js`), the form styles (`css/forms.css`), Maidenhead, UTM/UTMREF, haversine distance, ADI parsing/encoding, callsign list and repeater search, the data loader, the IndexedDB storage layer, DOM helpers (plain ES modules, node-tested where pure), the build-time data (`data/`, git-ignored) and the one vendored Leaflet. Tools import it by relative path (`../shared/…`). `scripts/single_file.py` is the stdlib bundler behind both single-file versions (`confirm-offline.html`, `adif-editor.html`); its import/export rules apply to shared modules too. Read `tools/shared/README.md` before changing it.
- **ADIF editor tool**: `tools/adif/` is a dependency-free client-side ADIF (`.adi`) log editor, served at `/tools/adif/` on oe1ebg.at. `index.html` loads plain ES modules (`js/`, plus `tools/shared/js/adif.js`); every loaded file is validated against ADIF 3.1.7 by `tools/shared/js/adif-validate.js` (`validateAdif()`, pure, data-driven by the generated `adif-spec-data.js`; valid = no error-severity issue; codes and the cross-check differences to adifmt/adif-checker in the tool's README), and re-checked as exported after edits (in idle time); the table body is virtualized (`js/table.js`), and `js/state.js` holds the log, the view and the per-record issue index with the view contract for search/filter code; `scripts/build_adif.py` generates the single-file `adif-editor.html` (git-ignored) that runs from `file://`. Background/design rationale lives in `tools/adif/README.md` (not published, see *Tool staging*).
- **SOTA Alerts Map tool**: `tools/sota-alerts/`, served at `/tools/sota-alerts/`: `index.html` loads plain ES modules (`js/`: API client, static-first summit lookup, alerts/filters, share link, popups and lists built with `el()`, the Leaflet map; plus `tools/shared/js/geo.js`, `prefs.js`, `dom.js`; Leaflet from `tools/shared/vendor/`), the pure ones node-tested in `tests/sota-alerts.test.mjs`. It's a live client of `api2.sota.org.uk` (SOTA's public API) — before extending its API usage, read `tools/sota-alerts/README.md` (design rationale, ToS considerations) and `tools/sota-alerts/AGENTS.md` (API call inventory, the static-first summit-coordinate lookup built by `scripts/fetch_summits.py`, and how to verify changes).
- **Notfunk-Meldebuch (draft, #31)**: `tools/notfunk/`, served at `/tools/notfunk/` (in the nav and llms.txt as a draft, together with its manual), an offline emergency traffic log for ÖVSV Notfunk / Krisenstab (SKKM): operations with a station code, messages with gapless numbers (`<code>-<n>`, taken in one storage transaction, never reused), status per direction with who and when (Eingang: erfasst → übergeben → übernommen; Ausgang: zur Übertragung → übertragen → Empfang bestätigt; beantwortet via a reply), the Meldesammelstelle's reference kept apart from the number, replies, revisions, Geschäftsbuch CSV, JSON backup, a help dialog (F1), and printouts via the print dialog (Meldeaufnahmeformular per message on one A4 page, empty form, message book). Same offline rules as the confirmation log (cache-first PWA on `tools/shared/js/sw-core.js`, single-file `notfunk-offline.html` via `scripts/build_notfunk.py`). The format is provisional until the Notfunkreferat Wien confirms it. Read `tools/notfunk/README.md` and its `AGENTS.md` first.
- **Manuals:** German user manuals with screenshots for the two offline tools, `docs/confirm-anleitung.md` and `notfunk-anleitung.md` (draft); each opens with a launch button for its tool and a short "Kurz: so geht's los". Each tool's header (`#manual-link`) and help (`#help-manual`) link to its manual (both hidden in the `file://` bundle). The tools overview and the manuals use the badge (`.tool-badges`, right under the heading) and action-row (`.tool-actions`: launch button in the apps' button shape with their soft accent tint, + secondary links) classes (`tools/shared/css/docs.css` in the bundle; the oe1ebg.at site styles them in its own `extra.css`). Keep their wording the same as the tools' UI and help.
- **Confirmation log (Bestätigungsverkehr)**: `tools/confirm/`, served at `/tools/confirm/`, is an offline logbook for check-in nets (operator/station header, auto UTC time, repeat check-ins, repeater per line, CSV/ADIF export), with an offline Austrian callsign list, the ÖVSV repeater list (all of Austria) for the log header, an offline location lookup (`js/location/`: Vienna addresses/landmarks/GIP place names/stops with colloquial and former names, places around Vienna, street corners and free-text reports, Austria-wide PLZ/Gemeinden/Bezirke with the Maidenhead locators they cover, UTMREF/MGRS input), UTMREF display and export (`tools/shared/js/utm.js`), and an offline map view (vendored Leaflet + build-time vector basemap, no tiles). It **must work 100% offline**: everything is built at build time, it is a cache-first PWA (`sw.js` on the shared `tools/shared/js/sw-core.js` + generated `precache.js`, with user-triggered updates via `tools/shared/js/offline.js`), and there is a generated single-file `confirm-offline.html` for `file://`/USB use. Data lives in IndexedDB and is never hard-deleted. Its JS is split into plain ES modules (`js/`, plus the location lookup in `tools/shared/js/location/`) so the node tests can import them. Read `tools/confirm/README.md` and `tools/confirm/AGENTS.md` before changing it.
